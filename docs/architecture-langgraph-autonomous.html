二、四个新角色：它们拿到什么、从哪来、拿不到什么

裁判只吹哨不下场；三个 agent 只提候选和理由，最终写账永远由确定性代码执行。

解析质检裁判 小模型

新建 · 只当裁判
  • 拿到什么：抽取结果 + 原文片段 + 校验预检结果。
  • 从哪来：规则通道与 LLM 通道的输出（ExtractedDocument）。
  • 拿不到什么：不改任何字段、不做抽取，只输出「过 / 不过 + 原因 + 重试建议」。
  • 闸门规则：不过 → 补救 agent，最多 2 次；仍不过 → PENDING_REVIEW。

补救 agent

新建 · 控制流自主
  • 拿到什么：裁判的失败原因 + 当前 RawDocument + 已重试次数。
  • 从哪来：质检闸门的条件边（这是现在代码完全没有的回路）。
  • 能调工具：reparse reocr_page reextract_fields，自己决定用哪个。
  • 拿不到什么：不能直接改金额、不能绕过裁判、不能超过重试上限。

模糊匹配 agent

新建 · 会用工具
  • 拿到什么：四级匹配没命中或多候选时的候选账单行 + 台账 + 费用名字典。
  • 从哪来：matcher.py 的结果（唯一命中时根本不打扰它）。
  • 能调工具：query_ledger lookup_charge_dict read_source，像业务员一样自己翻台账核原文。
  • 拿不到什么：不能新造账单号；证据不足就维持「未匹配」，理由写进 audit_trail。

AR/AP 判断 agent

新建 · 语义推理
  • 拿到什么：签发方 / 接收方 / MY_COMPANY / 收费方向四要素 + 原文证据。
  • 从哪来：posting 确定性核心判「角色不明」时才触发（明确时照旧走死规则）。
  • 能调工具：read_source query_ledger（看同一对手方的历史方向）。
  • 拿不到什么：不算金额、不改过账公式；只输出角色判断 + 理由，交回确定性核心执行。

三、工具层：全是现有模块包一层

agent 的「手」不新造轮子——每个工具就是对现有确定性模块的一次受控调用，入参出参都有 schema。

reparse

换参数重新解析整个文件。包 ingest/dispatcher + 各 loader。

reocr_page

只对指定页重新 OCR。包 ingest/ocr_client（自带重试与熔断）。

reextract_fields

带「缺什么」的反馈重抽指定字段。包 extract/llm_extractor。

query_ledger

按参考号 / 对手方 / 金额区间查台账。包 matching/ledger。

lookup_charge_dict

查费用名归一化字典（28 组）。包 normalize/charge_names。

read_source

按 locator 读原始文本片段当证据。包 models.RawDocument。

四、这个底子能用多少？

结论：约 85% 的代码原样保留。真正动的只有编排层（pipeline.py + agent.py 约 500 行改写成 StateGraph）， 外加新建裁判 / agent / 工具约 600–800 行。钱相关的模块一行不碰。

五、自主性的边界：哪儿放脑子，哪儿放规章

必须死规则（一行都不交给 LLM）

  • 金额加减与币种换算
  • ISO 6346 箱号校验位、单价 × 数量校验
  • 输出六字段 JSON 契约
  • 四级匹配的规则本体
  • AR/AP 过账公式（agent 只补「角色」这一个输入）
  • operation 判定公式与重复检测

允许自主（没有唯一正确答案的地方）

  • 解析质量差时「怎么补救」：重 OCR？换抽法？放弃？
  • 规则匹配不上时「像不像同一张账单」的推理
  • 记账角色不明时结合四要素的判断
  • 以上每一步的理由，全部写进 audit_trail 可审计
一句话原则：自主节点只产出「候选 + 理由」，最终落账永远由确定性代码执行；任何 agent 失效，整图退化为今天的纯规则流水线，照样能出合法 JSON。

六、落地顺序：每一步都可验证

1
先搬骨架，不改行为。

把现有 pipeline 逐站搬进 StateGraph 节点，删 agent.py 假并行。验证：89 个测试全绿、examples 输出逐字节一致。

2
加质检裁判 + 重试回路。

JUDGE_MODEL 小模型只吹哨；补救 agent 带反馈重试 ≤2 次。验证：构造坏 OCR 样例，看重试与转人工路径。

3
加模糊匹配 / AR/AP 判断 agent + 工具层。

只在规则搞不定的分支触发。验证：多候选样例、角色不明样例，audit_trail 里能看到推理理由。

4
评测对比收尾。

同一批 examples 跑新旧两版，对比 recall / precision / PENDING_REVIEW 率与耗时成本，写进 HARNESS 报告。

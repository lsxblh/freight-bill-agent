18 个节点，逐个走一遍

配套框架图的「节点详解」。每个节点都按同一套六问来讲：它拿到什么 / 东西从哪来 / 它干什么 / 它交回什么 / 它拿不到什么 / 出错怎么办。 绿色是原样保留的死规则，橙色是升级，青色是新增的 agent，红色是转人工兜底。

← 回到框架总图
死规则 · 原样保留（12） 升级 · 加入口（1） 新 agent（4） 转人工兜底（1）
RawDocument · 原始证据text / pages / tables / sha256 / 附件树。只搬原文，不懂语义。
→
ExtractedDocument / ChargeLine · 语义单据类型 / 双方 / 费用明细 / 标识符 / 置信度。规则+LLM 抽出来的。
→
OutputRecord · 标准输出题目六字段 + audit_trail。严格 JSON，契约不变。

状态就在这三层模型之间流动；下面按流程顺序，一站一站走。

第 1 段

拆包层 · 把文件变成原文

A → B → C，底子原样保留

A

输入文件

死规则cli.py · collect_input_files
它拿到什么用户给的一个/一批文件路径，或一个文件夹（EML / PDF / 图片 / Excel / Word）。
东西从哪来命令行 python -m shipping_billing run <文件>。
它干什么只把"要处理哪些文件"列出来：展开文件夹、去重、排序。像收发室先把今天要处理的信摞整齐，还没拆。
它交回什么一份文件路径清单。
它拿不到什么不看文件内容，不判断格式——那是下一站的事。
出错怎么办路径不存在 → 直接报错提示，不往下走。
B

dispatcher 按后缀路由

死规则ingest/dispatcher.py
它拿到什么一个文件路径。
东西从哪来A 的清单，逐个递过来。
它干什么看后缀决定交给哪个 loader：.eml→邮件、.pdf→PDF、图片→OCR、.xlsx→Excel、.docx→Word。这就是你之前问的"按后缀分流"，用路由/条件边实现，不是 LangGraph 内置。
它交回什么选定的 loader + 这个文件。
它拿不到什么不读内容，只看后缀；后缀不认识就标 unknown。
出错怎么办不支持的后缀 → 标记 unknown / 跳过，不拖垮整批。
C

解析成 RawDocument

死规则ingest/*_loader · ocr_client
它拿到什么文件 + 选定的 loader。
东西从哪来B。
它干什么把文件变成"原始证据"：PDF 读文本层、图片/扫描件走 OCR、Excel 读表格、EML 取头+附件递归；算 sha256 当缓存键。像把信拆开、把外文扫描件拍照存档，但还不翻译。
它交回什么RawDocument：text / pages / tables / metadata / 附件树 / sha256 / ocr_source。
它拿不到什么不理解语义、不抽字段，只"搬运原文"。
出错怎么办OCR 重试 3 次 + 熔断；读不出 → 抛异常被上层隔离。这也是补救 agent 能"重 OCR / 重解析"回到的一站。
第 2 段

抽取层 · 两条通道抓字段

D 规则 + E LLM 并行，各抓各的

D

规则抽取

死规则extract/rules.py
它拿到什么RawDocument 的 text / tables。
东西从哪来C。
它干什么正则 + 启发式抓核心：单号 / 日期 / 金额 / 箱号 / 费用行 / 交易双方。顺风局主力——干净固定的单据，它几乎全包。
它交回什么一份 ExtractedDocument 雏形（charges + identifiers + 部分语义字段），method=rules。
它拿不到什么没见过的模板、模糊措辞会抓不全；抓不到就留空，不臆造。
出错怎么办抓不到的字段置 null，交给 E 补位。
E

LLM 结构化抽取

死规则骨架里的 LLMextract/llm_extractor.py
它拿到什么RawDocument 文本 + 一份 JSON Schema（限定只能输出哪些字段）。
东西从哪来C（与 D 接力）。
它干什么提示词 | ChatOpenAI | 解析器，温度 0，补规则抓不到的语义字段：签发方 / 接收方 / 单据类型 / 模糊费用名。这是"翻译官"帽子。可选——没配 API key 就降级成空实现。
它交回什么另一份 ExtractedDocument 候选（LLM 视角），method=llm。
它拿不到什么不做最终决策，金额它说了不算；不碰匹配 / 过账。
出错怎么办重试 → 仍失败返回 None → 融合时退回纯规则，永不拖垮流水线。
第 3 段

质检闸门 · 新自主回路

F 裁判吹哨，H 补救重试（≤2），这是"自主应对"的核心

F

解析质检裁判

新 · 独立小模型graph/judge.py（新建）
它拿到什么D 和 E 的抽取结果 + 原始 RawDocument 供对照。
东西从哪来D / E。
它干什么裁判员独立小模型只判断"这解析够不够格让后续正常走"：关键字段齐不齐、金额跟原文对不对得上、有没有明显 OCR 错。只吹哨，不抽取、不返工。
它交回什么一个判定 pass / fail + 理由；fail 时指出"哪里不行"，当作补救的反馈。
它拿不到什么不改数据、不做抽取、不决定最终入账。
出错怎么办条件边：pass→G；fail 且重试<2→H；重试 2 次仍 fail→P 转人工。
H

补救 agent

新 · 控制流自主graph/agents.py（新建）
它拿到什么F 的 fail 理由 + RawDocument + 当前抽取结果 + 重试计数。
东西从哪来F。
它干什么裁判员自己决定怎么补救，选工具：reparse 换解析 / reocr_page 重 OCR 某页 / reextract_fields 带反馈重抽。不像旧代码只会"跳过/转人工"，它会"自己想办法再来一次"。
它交回什么一个动作决策 + 工具调用后的新 RawDocument / 抽取结果，回到 C 重新走一遍。
它拿不到什么不能无限重试（≤2）；不能跳过质检直接入账；不能改钱。
出错怎么办重试耗尽 → 交回 F → P 转人工。
第 4 段

融合 + 归一化 · 把两份结果合成一份标准件

G 裁决合并，I 查字典标准化

G

融合 merge

死规则extract/merge.py
它拿到什么D（规则）和 E（LLM）两份结果。
东西从哪来F 判定通过后。
它干什么规则为准、LLM 补位、冲突降级：数字字段以规则/原文为准；语义字段规则缺才用 LLM；冲突保留规则值 + warning + 置信×0.8；LLM 补的费用封顶 0.7。
它交回什么一份合并后的 ExtractedDocument。
它拿不到什么不重新抽取，只"合并裁决"。
出错怎么办冲突记 warning，不崩。
I

归一化

死规则normalize/charge_names · currency
它拿到什么合并后的 ExtractedDocument（charges 的 raw_name 等）。
东西从哪来G。
它干什么费用名查字典（28 组）→标准名；币种标准化；付款条款归一。注意：归一化是字典（代码）的活，不是 agent 的活。
它交回什么charges 的 charge_item 标准化 + standardized 标记。
它拿不到什么字典没收录的不瞎翻——保留原名 + 低置信 + 提示。
出错怎么办未知名 → 保留原名、打低置信，转人工核对。
第 5 段

匹配 · 这笔是不是老账单

J 四级死规则先试，搞不定交给 K 模糊匹配 agent

J

四级匹配 + 金额二次判别

死规则matching/matcher.py
它拿到什么一条 ChargeLine + ExtractedDocument + Ledger（台账）+ settings。
东西从哪来I，逐条费用递过来。
它干什么按优先级试四条规则：①单据编号+费用名 ②提单号+费用名+币种 ③订舱号+费用名+币种 ④箱号+交易双方+日期+金额。同规则多命中用金额距离选最接近；先按记账主体隔离台账。
它交回什么MatchResult：matched / line / rule / score / conflicts / candidate_count。
它拿不到什么不创造台账记录；字段冲突只记录，不擅自改。
出错怎么办条件边：唯一命中→L；无命中 / 多候选→K。
K

模糊匹配 agent

新 · 会用工具graph/agents.py（新建）
它拿到什么J 没搞定的 ChargeLine + 候选 + 台账访问 + 原文。
东西从哪来J（无命中 / 多候选）。
它干什么裁判员用工具 query_ledger 翻台账 / read_source 核原文 / lookup_charge_dict，推理"这条到底对应哪笔，还是新账单"。像个会查资料的老业务员，不是干瞪眼。
它交回什么一个匹配候选 + 理由 + 置信度（写进 audit_trail），交回 L。
它拿不到什么不直接写台账；拿不准就标低置信 / 转人工，不硬配。
出错怎么办实在定不了 → 建议当新账单，或转人工。
第 6 段

过账 · 应收还是应付

L 确定性核心先判，角色不明交给 N 四要素推理

L

AR/AP 过账 · 确定性核心

升级 · 加入口finance/posting.py
它拿到什么匹配结果 + issuer / recipient + 记账主体 + document_type + amount_sign。
东西从哪来J 或 K。
它干什么三步：①定角色（记账主体是签发方还是接收方，相似度≥0.7）②基础方向（我方签发→AR，接收→AP）③Credit / 红字反转。升级点：新增"接受 agent 判出的角色"入口。
它交回什么PostingDecision：posting_type / role / confidence / reasoning。
它拿不到什么角色不明绝不猜 → None + 转人工。
出错怎么办条件边：角色明确→M；角色不明→N。
N

AR/AP 判断 agent

新 · 四要素推理graph/agents.py（新建）
它拿到什么L 定不了角色的情况 + 四要素（签发方 / 接收方 / 记账主体 / 收费方向）+ 原文上下文。
东西从哪来L（角色不明）。
它干什么裁判员结合四要素推理"我方到底是收钱还是付钱"，读合同措辞等上下文。
它交回什么一个角色 / 方向候选 + 理由（写进 audit_trail），交回 M。
它拿不到什么推理不出就维持 None 转人工，不猜。
出错怎么办仍不明 → P 转人工。
第 7 段

校验 · 判定 · 输出

M 挑毛病，O 定操作，P 兜底，Z 装配，OUT 出 JSON

M

校验 + 置信度

死规则validation/validators.py
它拿到什么ChargeLine + ExtractedDocument + PostingDecision。
东西从哪来L 或 N。
它干什么五项校验（金额有效 / 币种 ISO4217 / 明细 vs 合计 / OCR 混淆 / 重复提取）+ ISO6346 箱号校验位 + 单价×数量。产 Issue（error/warning/info），汇总置信度。
它交回什么issues 清单 + 置信度。
它拿不到什么只挑毛病，不决定入账（那是 O 的事）。
出错怎么办有 ERROR → has_blocking → 后面判 PENDING_REVIEW。
O

operation 判定

死规则pipeline_utils.py
它拿到什么匹配结果 + issues + 置信度。
东西从哪来M。
它干什么定 operation：匹配到且无变化→NO_CHANGE；匹配到有更新→UPDATE；没匹配到→CREATE；有阻断 ERROR / 低置信 / 冲突→PENDING_REVIEW。
它交回什么operation 四值之一。
它拿不到什么不改金额 / 方向。
出错怎么办拿不准 → PENDING_REVIEW。
P

PENDING_REVIEW 转人工

兜底pipeline_utils.py
它拿到什么前面各站标记的"不可信 / 拿不准"记录 + 原因。
东西从哪来F（重试耗尽）/ O（阻断）。
它干什么不自动入账，贴"待人工复核"标签，写清缺什么 / 可能是什么 / 证据在哪。像质检员把可疑产品放一边，既不悄悄放行也不直接扔。
它交回什么一条 operation=PENDING_REVIEW 的记录。
它拿不到什么不替人做决定。
出错怎么办它就是兜底，不再往下出错。
Z

装配 OutputRecord + audit_trail

死规则pipeline.py · assemble
它拿到什么operation + 单据信息 + 交易双方 + 费用明细 + 财务属性 + 各站理由 / 证据。
东西从哪来O 或 P。
它干什么按题目六字段组装 OutputRecord；把 agent 的理由、匹配规则、置信度、来源、field_changes 塞进 audit_trail。
它交回什么一个 OutputRecord。
它拿不到什么不新增顶层字段——扩展全进 audit_trail。
出错怎么办装配失败 → 隔离该条，整批继续。
OUT

合法 JSON 输出

死规则models.to_json_dict
它拿到什么OutputRecord 列表。
东西从哪来Z。
它干什么to_json_dict，严格照题目契约输出；写文件 / 打印。
它交回什么最终 JSON，契约不变。
它拿不到什么不再改内容。
出错怎么办终点，无下游。

一句话把 18 站串起来

拆包（A→B→C）把文件变原文 → 两条通道抽字段（D 规则 + E LLM）→ 质检裁判 F 吹哨，不行就让 H 补救重试（≤2）→ 行了就 融合 G + 归一化 I → 四级匹配 J，搞不定交 K → AR/AP 过账 L，角色不明交 N → 校验 M → 定 operation O → 不可信走 P 转人工 → 装配 Z → 出 JSON OUT。

记住那两顶帽子：翻译官（E，把单据变结构化数据）+ 裁判员（F/H/K/N，在规则拿不准处做判断）。其余全是死规则守着"钱算得对、输出合契约"。

四个条件边（自己拿主意的地方）：质检闸门（F）、匹配结果（J）、角色明确与否（L）、重试计数（H→C 回路）。
